The Critic Notebook

I implemented CRITIC-R1 (arXiv 2605.29886): a small language model trained with reinforcement learning to critique retrieval-augmented answers by saying whether an answer is wrong, where it went wrong and how to fix it. Then I took what survived measurement and put it into a live search engine. These are the deep-learning and RL ideas the work depended on, in the order they came up, each with the maths and the number it produced on this project.

Structured output as an action space

A critic that writes free prose can't be scored automatically, and you can't run RL without a score. CRITIC-R1 makes the critic write four tags in a fixed order, which turns "critique this answer" into choosing from a small, checkable action space.

<verdict>CORRECT | INCORRECT | UNSURE</verdict>
<location>none | search:stepK | information:DocK | think:stepK | answer</location>
<reason>...</reason><fix>...</fix>

coupling rule:  verdict = CORRECT      <=>  location = none
                verdict = INCORRECT/UNSURE  =>  location set, reason non-empty

The parser is the first reward. Following the paper's Algorithm 1, an output that fails to parse gets a flat penalty and nothing else is scored, so there is no partial credit for a good reason inside broken tags.

r_format = +0.2   if parse(y) succeeds
R(y)     = -1.0   if parse(y) fails      (gamma = 1.0, all other terms skipped)
What brokeThe untrained 1.5B model produced a strictly valid critique 12% of the time. Under Algorithm 1 that means 88% of early rollouts score exactly −1.0, every sample in a group scores the same, and GRPO gets no gradient at all (see entry 6). This "format cliff" is why RL can't start cold: it needs a supervised warm start first.

Labels for free from a QA dataset

A critic needs examples of right and wrong answers with known causes. HotpotQA's distractor setting supplies them: each question comes with 10 paragraphs, exactly 2 of which hold the answer. I had the 1.5B model answer each question over those paragraphs, then labelled its answer by comparing it with the gold answer.

P  = |pred tokens ∩ gold tokens| / |pred tokens|
R  = |pred tokens ∩ gold tokens| / |gold tokens|
F1 = 2PR / (P + R)

verdict = CORRECT    if F1 ≥ 0.8
          INCORRECT  if F1 ≤ 0.3
          UNSURE     otherwise

example: gold "Charles Dickens", pred "Dickens"
         P = 1/1, R = 1/2, F1 = 0.667  -> UNSURE

The two gold paragraph indices give a ground truth for where an answer should have looked. That is what makes localisation measurable later: if the critic names information:Doc4 and Doc4 is a gold paragraph, it found the evidence the answer needed.

The training and evaluation trajectories come from different HotpotQA splits, so no evaluation question was ever seen in training.

Entry 3 LoRA · Parameter-efficient fine-tuning
18.5M
trainable parameters out of 1.54B (1.2%)

LoRA: training 1.2% of a model

Full fine-tuning doesn't fit. In bf16 with Adam, a 1.5B model needs about 3 GB of weights, 3 GB of gradients and 12 GB of fp32 optimizer state before a single activation is stored. LoRA freezes the original weights and learns a low-rank correction beside each linear layer.

h = W0 x + (alpha / r) * B A x

W0 : out x in    frozen
A  : r x in      trained, random init
B  : out x r     trained, init 0   -> the model starts exactly as the base model
params per layer = r * (in + out)

Qwen2.5-1.5B, r = 16, alpha = 16, all linear layers, per transformer block:
  q, o        16 * (1536 + 1536) = 49,152   each
  k, v        16 * (1536 +  256) = 28,672   each
  gate, up    16 * (1536 + 8960) = 167,936  each
  down        16 * (8960 + 1536) = 167,936
  block total 659,456  x 28 blocks = 18,464,768

LoRA had a second payoff in RL. The KL penalty in entry 7 needs a frozen reference model, and with LoRA that reference is the same weights with the adapter switched off. It costs no memory and no second model load.

with model.disable_adapter():          # reference policy = base weights
    ref_logp = token_logprobs(model, ids)
Entry 4 Supervised fine-tuning · Loss masking
6.83 → 4.28 GB

Supervised warm start and loss masking

Before RL, the critic was taught the format by imitation on teacher-written critiques. The loss is ordinary next-token cross-entropy, counted only over the critique tokens. The prompt (question plus ten paragraphs) is context; training the model to reproduce it would waste capacity on copying.

L = -(1/|T|) * sum over t in T of  log p_theta(y_t | y_<t, x)
T = positions of the target critique (prompt positions are masked out)

The mask also cut memory. The final projection to the vocabulary is the biggest activation in the network, and the default computes it at every position, including the 1,700 prompt tokens whose loss is then thrown away.

logits for one sequence = positions x vocab x 4 bytes
                        = 1792 x 151,936 x 4  ≈ 1.09 GB  (plus the same again for its gradient)

model(input_ids, logits_to_keep=len(target) + 1)   # project only the target positions
What heldStrict format validity went from 12% to 49.5% on full critiques, and to 99% once the verdict was supplied. That was enough for RL rollouts to produce groups with different rewards.

garbage
what rollouts looked like until generation got its own mode

Gradient checkpointing and the KV cache

Backpropagation needs every intermediate activation from the forward pass. Gradient checkpointing keeps only the activations at block boundaries and recomputes the rest during the backward pass, trading about one extra forward pass (~33% more compute) for a large cut in activation memory.

RL alternates two very different workloads: generating rollouts and training on them. Generation relies on the KV cache, which stores each past token's keys and values so that each new token costs one step instead of re-running the whole prefix.

tokens processed to generate T new tokens after a prompt of length P:
  with KV cache     P + T
  without           sum_{k=1..T} (P + k)  ≈  T*P + T^2/2
What brokeWith checkpointing on, the library turns the cache off, and the first GRPO rollouts came back as fluent nonsense. Every reward was −1.0 and the run looked like it was "learning" nothing. The fix is a context manager that puts the model into a correct generation state and restores the training state afterwards.
@contextmanager
def _generation_mode(self):
    self.model.gradient_checkpointing_disable()
    self.model.config.use_cache = True
    self.model.eval()
    try:
        yield
    finally:
        self.model.gradient_checkpointing_enable()
        self.model.config.use_cache = False
        self.model.train()
Entry 6 GRPO · Policy gradients · Advantages
21%
of groups at worst had identical rewards and taught nothing

GRPO: RL without a value network

PPO estimates how good a sample was relative to expectation using a learned value network, which is a second model as large as the policy. GRPO (Group Relative Policy Optimisation) removes it: sample several completions for the same prompt and use the group's own mean as the baseline. Because every member of a group saw the identical prompt, prompt difficulty cancels out.

for each prompt x, sample G completions y_1..y_G, score rewards r_1..r_G

A_i = (r_i - mean(r)) / (std(r) + eps)          group-relative advantage

rho_i = pi_theta(y_i | x) / pi_old(y_i | x)      importance ratio (per token)
L = -mean[ min(rho * A, clip(rho, 1 - 0.2, 1 + 0.2) * A) ] + beta * KL

example, G = 4:  r = [0.7, -1.0, 0.7, 0.5]
  mean = 0.225   std = 0.712
  A    = [+0.67, -1.72, +0.67, +0.39]
  -> push up the three good critiques, push the broken one down hard

I ran one update per batch of rollouts, so the ratio is exactly 1 in value and the clip never activates. The gradient still flows through rho, and it reduces to the plain policy gradient ∇ log π · A. The trainer refuses a configuration with more inner epochs, because the "old" log-probs it would need were never stored.

What brokeA group whose samples all score the same has standard deviation 0. Dividing float noise by ~0 manufactures a large, meaningless gradient. Those groups now get advantage exactly 0. The share of flat groups, which reached 21% in the localisation stage, became the most useful health metric of the run: it is the fraction of compute that taught nothing.

Settings: G = 4, 2 prompts per step, learning rate 1e-6, clip 0.2, KL coefficient 0.003, LoRA r16 α16. The paper's settings, scaled from 3B on two A100s to 1.5B on one 8 GB laptop GPU.

The KL leash and the k3 estimator

RL with a learned or rule-based reward will exploit any gap in the reward. A KL penalty keeps the policy close to the reference model, so it can only win reward with outputs the base model already finds plausible. The exact KL needs a sum over the whole vocabulary at every step; instead it is estimated from the sampled tokens.

d  = log pi_ref(token) - log pi_theta(token)

k1 = -d                 unbiased, but negative half the time (noisy)
k3 = exp(d) - d - 1     unbiased and always ≥ 0   (Schulman's estimator)

check: d = 0     -> k3 = 0       (policies agree)
       d = 0.5   -> k3 = 0.149
       d = 10    -> k3 = 22,015  <- one token can dominate the batch
What brokeA smoke run logged KL = 70 from a single token where the two models disagreed sharply. The exponential turns one outlier into a gradient that swamps the reward. Clamping d to ±10 bounds it without changing the estimator anywhere a healthy run operates.
d  = torch.clamp(ref_lp - new_lp, -10.0, 10.0)
kl = torch.exp(d) - d - 1.0
loss = (pg + cfg.kl_coef * kl).mean()
Entry 8 Reward design · Expected value · Reward hacking
0 / 200

When the reward says "always say CORRECT"

The verdict reward is the paper's Table 7 payoff matrix. It punishes calling a correct answer wrong (−1.0) far more than calling a wrong answer correct (−0.3), because a false alarm sends a good answer into a rewrite that can break it.

truth ↓ / predicted →CORRECTINCORRECTUNSURE
CORRECT+0.7−1.0−0.1
INCORRECT−0.3+0.5−0.1
UNSURE+0.1−0.20.0

Before training on any reward, compute what the constant policies earn. On this data (33% correct, 51% incorrect, 16% unsure):

E[always CORRECT]   = 0.33(0.7)  + 0.51(-0.3) + 0.16(0.1)  = +0.094
E[always INCORRECT] = 0.33(-1.0) + 0.51(0.5)  + 0.16(-0.2) = -0.107

A critic that can't tell right from wrong maximises reward by approving everything. Measured directly, the 1.5B model's ability to separate right from wrong answers was AUC 0.447, below the 0.5 of a coin flip. GRPO did exactly what it was asked: it found the best policy available to a model with no signal, which was to say CORRECT every time.

The lessonThis wasn't a bug in the optimiser. The reward was being maximised honestly. When RL "collapses", check the constant-policy baseline of the reward and whether the model has any signal to learn from before blaming the algorithm.

Reward shaping and gated rewards

The paper's second stage, DQA, rewards the quality of the diagnosis: a correct location, a reason that matches the reference reason, a fix that matches the reference fix. Text similarity scores are mapped through a convex curve so that vague, half-relevant text earns almost nothing.

r = R_max * (exp(beta * s) - 1) / (exp(beta) - 1)      s in [0, 1], beta = 3

s = 0.3  ->  8% of R_max
s = 0.5  -> 18%
s = 0.9  -> 73%

The diagnosis reward is gated on the verdict being right, so a model can't earn diagnosis credit for explaining an error that doesn't exist:

R = r_format + r_verdict + 1[verdict_pred = verdict_true] * (r_location + r_reason + r_fix + r_aux)
What brokeAfter entry 8 the critic never predicted INCORRECT, so the gate never opened and stage 2 received no signal. The fix was to prefill the verdict (the prompt ends with <verdict>INCORRECT</verdict><location>) and train localisation on its own, 343 located examples. The verdict question moved somewhere else entirely (entry 12).

One deliberate deviation from the paper: where the reference reason was a template rather than a teacher-written explanation, the reason and fix rewards are switched off, so the model isn't trained to imitate boilerplate.

~13×

Living inside 8 GB

On Linux, running out of GPU memory raises an error. On Windows, the NVIDIA driver by default spills the overflow into system RAM over PCIe. Nothing fails; everything gets about 13 times slower, so a training run that should take an hour looks hung. I treated free VRAM as a budget instead.

  • Headroom check. Every generation batch requires 0.8 GB free before it starts. If an allocation fails anyway, the batch is halved and retried.

  • One sample per backward pass. Batched training pads sequences on the left, which shifts where each completion starts. Processing one concatenated prompt+completion at a time with gradient accumulation removed both the padding waste and an indexing bug that came with it.

  • Truncate from the left. Prompts longer than 1,536 tokens get cut. Cutting from the right removed the assistant cue at the end of 37% of long prompts, so the model was asked to continue a paragraph instead of writing a critique. Cutting from the left drops the least relevant paragraph text and keeps the instruction.

  • Stop strings. Generation stops at </fix> instead of running to the 160-token limit, which shortens most rollouts.

Measuring it honestly

The localisation benchmark gives every critic the same held-out wrong answers, prefills the verdict, and counts a hit when the critic names one of the two gold paragraphs. Random guessing hits about 20.5% of the time. The first run used 100 questions. When that turned out too small to separate the models, I generated 250 more that no earlier analysis had touched and reran every arm on them.

Qwen2.5-1.5B, untrained44.0%44.0%[38.0, 50.2]
+ SFT40.0%48.8%[42.7, 55.0]
+ SFT + GRPO (final checkpoint, step 100)46.0%51.2%[45.0, 57.3]

Three tools did most of the work.

Wilson interval (better than p ± 1.96*sqrt(p(1-p)/n) at small n or extreme p):
  centre = (p + z^2/2n) / (1 + z^2/n)
  half   = z * sqrt(p(1-p)/n + z^2/4n^2) / (1 + z^2/n)

Exact McNemar (two critics on the SAME questions):
  b = A right, B wrong      c = A wrong, B right
  under H0 each discordant pair is a fair coin:
  p = 2 * P(Binomial(b + c, 0.5) ≤ min(b, c))
  untrained vs SFT+GRPO, fresh 250:  b = 20, c = 38  ->  p = 0.025
  SFT vs SFT+GRPO, fresh 250:        b =  3, c =  9  ->  p = 0.146

AUC (does the score rank wrong answers above right ones?):
  P(score(random wrong answer) > score(random right answer))
  0.5 = coin flip; measured 0.447 for the verdict

McNemar beats comparing two proportions here because both critics answer the same 100 questions. The paired test discards question difficulty, which is most of the variance.

What the numbers supportAt n = 100 no difference between the models was significant, which is why the second set exists. On the fresh 250, the fully trained critic beats the untrained model by 7.2 points (p = 0.025). GRPO beat SFT on both sets (8 to 2, then 9 to 3 discordant pairs), but neither set alone is significant. Pooled over all 345 it reaches p = 0.0075, and I report that only with the caveat that 95 of those questions were also used in the first run.

gpt-oss-20b shows the benchmark's blind spot. Given the same prompt, it usually blamed the final answer step, which the schema allows but the benchmark doesn't count as a hit. When it did name a document, it was right 82% of the time. One number would have hidden that, so both are reported.

who decides each half in production

From research artifact to product

The experiments split the critic's job in two. Deciding whether an answer is wrong had no signal at this scale. Saying where it went wrong, once you know it is wrong, worked at twice chance. So ResearchOS v2 divides the job the same way.

  • When: v1's existing confidence gate (mean of the top-5 reranker scores) decides that a result is weak. It already separates in-corpus from out-of-corpus queries cleanly, so the critic is never asked to judge.

  • Where and how to fix: a CRITIC-R1-format diagnosis names the retrieved paper that let the search down, says why, and proposes a query to run instead. The user sees it as a "Try: …" button.

The production diagnoser is gpt-oss on Groq rather than the fine-tuned 1.5B model, because the 1.5B model would take 15–30 seconds on the free CPU host. The trained critic stays as the measured research artifact. Every production diagnosis goes through the same strict parser the critic was trained against, and one that cites a document it wasn't shown is suppressed. It runs under a 6-second budget behind a circuit breaker, so it can never make a v1 answer slower or worse.

The ablation that keeps it honest

If a diagnosis "fixes" a failed search, the gain might come from an LLM rephrasing the query, not from reading what went wrong. So the evaluation has a control arm that rewrites the query with the same model and never sees the retrieved documents, and it counts harms (a search v1 got right that the new query loses) as well as rescues.
